Technical Architecture

How the automation actually works.

This document maps every step of the project spin-up to the specific API calls, data flows, and integration points that make it happen. Each automated step cites the Smartsheet or Microsoft Graph endpoint that powers it, and each manual checkpoint documents the platform limitation that requires a person.

Data Safety — What Touches the Sheets

A report is a read-only view of data from one or more sheets. Changing a report's filter or name never modifies the underlying sheet data. The only operation in this automation that permanently removes data is the project plan trim.

Impact of every API call on source data

Safe — No data change

Report filter update (PUT /reports/{id}/definition) — Changes which rows the report displays. Does not add, modify, or delete any data in the source sheets.

Safe — No data change

Report create / delete (POST /reports, DELETE /reports/{id}) — Creates or removes a view object. Source sheets are completely unaffected. Deleting a report does not delete any rows.

Safe — No data change

Report publish (PUT /reports/{id}/publish) — Generates a read-only URL. Does not modify source data.

Safe — No data change

Column hide (PUT /sheets/{id}/columns/{id} with hidden: true) — Hides a column from the default view. The column and all its data remain intact. Fully reversible.

Intentional write

Cell update (PUT /sheets/{id}/rows) — Writes the project name and number into specific cells. This is the intended behavior — the same values a person would type manually.

Permanent deletion

Row deletion (DELETE /sheets/{id}/rows) — Used to trim the project plan. This is the only operation that permanently removes data. Rows cannot be recovered once deleted. The script logs row IDs before deletion and a confirmation checkpoint is recommended in early runs.

Prerequisites & Project Structure

The automation works with the existing project folder structure. The New GEN009 template sheet is copied into the project's folder, and the script then finds and configures the artifacts that already exist there.

Template Location

The New GEN009 sheet is the single template that gets copied for each new project.

  • Workspace: CMR Backoffice
  • Folder: New project Spin up
  • Sheet: New GEN009
  • Full path: workspaces/CMR Backoffice/New project Spin up/New GEN009
  • Only this sheet is copied — not the entire workspace

Project Folder Structure

When a new project is spun up, its artifacts live in the Z-Active Projects workspace.

  • Destination: workspaces/Z-Active Projects/{Project Name - Project Toolkit}
  • 2 reports sit in the main Project Toolkit folder
  • 3 reports sit in the Dashboard Reports subfolder
  • Project plan, orders sheet, and dashboard also exist in this folder

Intake Form Changes

Two fields must exist on the project intake sheet so the script has the data it needs.

  • Project Type — dropdown with values: Commercial, Residential, Patterson. Drives which plan section to keep and whether to hide the Patterson column. Does not exist on the current form; must be added.
  • Approval Status — a column that changes to "Approved" when the project is greenlit. The webhook watches this column.

Licensing Requirements

The Smartsheet account must support API access and the required add-ons.

  • Smartsheet plan: Business or Enterprise (required for API and webhooks)
  • Dynamic View: premium add-on (required for the external sharing workflow)
  • Microsoft Graph: Entra app registration with Files.ReadWrite scope for OneDrive operations

Trigger: How the Automation Starts

The process begins when a Smartsheet alert email arrives in the inbox. The email contains the project name, number, and the keywords "alert," "new project onboarding," "set filters," and "spin up new projects." We need to detect that email and extract the project details from it. Three approaches are available, each with different trade-offs.

Option A

Monitor the inbox directly

The automation watches the existing inbox for Smartsheet alert emails. When one arrives, it parses the structured table inside the email body to extract the project name and number, then starts the control script. No change to the user's workflow.

How it works
  • Microsoft Graph API — webhook subscription on the inbox that fires on new email
  • Filter by sender/subject — check for Smartsheet alert keywords
  • Parse the email body — extract Project Number and Project Name from the structured HTML table
  • Start the control script — pass project name, number, and type to the automation
Medium setup effort
Option B

Web app — paste and trigger

A simple web page where the user pastes the project name and number and clicks a button to start the automation. The most reliable option — no email parsing needed, and the user stays in control of when each run starts.

How it works
  • Simple web page — form with project name, number, and optional project type dropdown
  • User pastes the values — copied directly from the alert email
  • Click "Run" — form submits to the callback server, which starts the control script
  • Live status — page can show automation progress in real time
Low setup effort
Option C

Forward to a dedicated email

The user forwards the alert email to a dedicated address that we monitor. As soon as the email arrives, the automation starts. The inbox is dedicated to this one purpose, so no filtering is needed.

How it works
  • Dedicated inbox — e.g., spinup@cmr-design.com
  • Microsoft Graph webhook — every incoming email triggers the callback
  • No filtering needed — every message is a trigger, zero false positives
  • Parse the email body — same structured table as Option A
  • User action — forward the alert email, one extra step
Medium setup effort
All Options

What happens after the trigger fires

Automated

Regardless of which trigger option is used, the result is the same: the project name, number, and type are extracted and passed to the control script. The script then reads the Master Project List to confirm the project details and proceeds to Phase 1.

GET
/sheets/{sheetId}/rows
Read the Master Project List row to confirm the project details and extract the project type (commercial, residential, Patterson). This validates the email data against the source of truth. Smartsheet API docs ↗
Project type is not in the email. The Smartsheet alert email contains the project name and number but not the project type. The script reads the project type from the Master Project List row (or from the intake form, if the project type field has been added). This is why the intake form change is a prerequisite.
Combining options is fine. Option B (web app) can coexist with Option A or C. The web app is useful as a fallback, a manual re-run tool, or a way to monitor progress. The email-based options (A and C) handle the hands-free case.

Phase 1 — Copy the New GEN009 Template

The script copies the New GEN009 sheet from the CMR Backoffice workspace into the project's folder in Z-Active Projects. This is a single sheet copy, not a workspace copy. The other artifacts already exist in the project's folder.

Phase 1

Copy the New GEN009 sheet into the project folder

Automated

The New GEN009 template sheet is copied into the project's folder at workspaces/Z-Active Projects/{Project Name - Project Toolkit}. The copy is named using the project name followed by "Gen 009" (e.g., "1815 Lakewood Road Gen 009"). The include parameter carries over data, filters, forms, and conditional formatting rules from the template.

POST
/sheets/{sheetId}/copy
Copy the New GEN009 sheet. Set newName to {Project Name} Gen 009. Set destinationType to folder and destinationId to the project toolkit folder ID. Use include with values like data, filters, forms, rules. Smartsheet API docs ↗
Template location: workspaces/CMR Backoffice/New project Spin up/New GEN009. The sheet ID is resolved at setup time and stored as configuration.
Destination folder: workspaces/Z-Active Projects/{Project Name - Project Toolkit}. The folder ID is determined by searching for the project name in the Z-Active Projects workspace.
What the copy carries: all rows, columns, formulas, conditional formatting, saved filters, and forms. What it does NOT carry: cell history. The original template is never modified.

Phase 2 — Configure the Checklist & Plan

After the sheet copy, the control script writes the project-specific data into the checklist, hides non-applicable columns, and trims the project plan to the correct section.

Step 2a

Write project name and number into the checklist

Automated

The project name and number from the intake row are written into the designated cells at the top of the new checklist sheet.

GET
/sheets/{sheetId}/columns
Resolve column IDs for the project name and project number columns. Smartsheet API docs ↗
PUT
/sheets/{sheetId}/rows
Update the target row cells with the project name and number. Up to 500 rows per call. Smartsheet API docs ↗
Data safety: This writes the same values a person would type manually. No existing data is overwritten — these cells are empty in the template copy.
Step 2b

Hide the Patterson column for non-Patterson projects

Automated

If the project type is not Patterson, the Patterson column is hidden on the checklist sheet. Safe and reversible — the column is not deleted, just hidden from the default view.

PUT
/sheets/{sheetId}/columns/{columnId}
Set "hidden": true on the Patterson column. Requires ADMIN_SHEETS scope. Hiding is reversible. Smartsheet API docs ↗
Data safety: Hiding a column does not delete or modify any data. The column and all its cell values remain intact. Unhiding is a single click.
Step 2c

Trim the project plan to one section

Automated

The CMR Project Plan contains three sections (commercial, residential, Patterson). The script deletes the two sections that do not match the project type, keeping only the relevant one.

GET
/sheets/{sheetId}
Read the plan sheet to identify the row IDs for each section. The script maps project type to which row ranges to delete. Smartsheet API docs ↗
DEL
/sheets/{sheetId}/rows
Delete the non-applicable section rows. Maximum 10 rows per request, so batch into groups of 10. This is the only operation in the entire automation that permanently removes data. Smartsheet API docs ↗
Data safety: Row deletion is irreversible. The script logs the row IDs being deleted and their content before deletion. A confirmation checkpoint in early runs is recommended. A safer alternative for future consideration: pre-build three template variants (one per type) and copy the correct one, avoiding destructive deletes entirely.

Phase 3 — Configure the Five Project Reports

The five reports already exist in the project's folder. The script finds them by name, updates each filter to the new account number, and creates a correctly-named replacement. Two reports are in the main Project Toolkit folder; three are in the Dashboard Reports subfolder.

Step 3a

Find and update each report's filter

Automated

The script searches for the five reports by name. Two are in the main Project Toolkit folder; three are in the Dashboard Reports subfolder. For each report, the script reads its current filter definition, swaps the old account number for the new project number, and writes the modified definition back.

GET
/folders/{folderId}/reports or /search?query=Update+Project+Filter
Find the five reports. Two in the main folder, three in Dashboard Reports. Double-curly-brace naming convention makes them reliably searchable. Smartsheet API docs ↗
GET
/reports/{reportId}
Get the report's current definition including its filter criteria. The script must read the existing definition before modifying it — the PUT is a full replace, not a patch. Smartsheet API docs ↗
PUT
/reports/{reportId}/definition
Replace the report's filter criteria with the new account number. Supports operators like EQUAL, CONTAINS, IS_ONE_OF, with nested AND/OR up to three levels. Must send the entire modified definition. Smartsheet API docs ↗
Data safety: Updating a report's filter definition only changes which rows the report displays. It does not add, modify, or delete any data in the source sheets.
Step 3b

Create reports with the project-specific name

Automated

The Smartsheet API does not support renaming an existing report. To get reports named with the project number (which serves as the visual confirmation that the report is done), the script creates each report fresh with the correct name and then applies the filter definition.

POST
/reports
Create a new report with the project-specific name (up to 50 characters). Name is set at creation time — the only way to get the correct name, since renaming is not supported. Smartsheet API docs ↗
PUT
/reports/{reportId}/definition
Apply the same filter definition (from Step 3a) to the newly created report.
DEL
/reports/{reportId}
Delete the original template-named report now that the correctly-named replacement exists. Smartsheet API docs ↗
Data safety: Creating a new report does not modify any source sheets — it creates a new view object. Deleting the old report removes the view, not the underlying data. No rows, columns, or cell values in any source sheet are affected.
Why this three-step pattern: The API does not support PUT /reports/{id} for renaming. POST /reports accepts a name at creation time. So: create with the right name, copy the filter definition, then delete the template-named original.

Phase 4 — Publish & OneDrive

The orders report is published and its link is stored in the project sheet. The two OneDrive folders are copied from templates and renamed to the project name.

Step 4a

Automated

Phase 5 — Human Checkpoints

Four steps require a person. Two are platform blockers (dashboard widgets and Dynamic View have no API), and two are intentional cost decisions (sharing and contract verification are faster to do manually than to automate).

Platform Blocker

Dashboard: paste the Orders report link

No API for widget editing

Smartsheet does not allow outside tools to change what appears on a dashboard. The widgets field on a Sight is read-only — attempting to write it returns error 1008. The automation prepares the Orders report link in the project sheet's Link column; a person copies it and pastes it into the dashboard widget.

Time: about one minute per project.

Redesign option: If the dashboard uses native Smartsheet report widgets instead of web content widgets, this manual step is eliminated entirely.
Platform Blocker

Dynamic View: create, filter, and share

No API for Dynamic View

Dynamic View has no API, no MCP tool, and no Bridge module. A person must complete this setup by hand — creating the Dynamic View (by copying the most recent one), building the Orders sheet filter (saved filters cannot be created via API either), setting the filter to the account number, domain-sharing to cmr-design.com, and pasting the Dynamic View link into the dashboard.

Time: a few minutes per project.

Timing dependency: The Orders sheet filter must be created and saved before opening Dynamic View, and it takes several seconds to propagate.
Cost Decision

Sharing with the right teammate

Kept manual for cost

The Smartsheet API can share a sheet and send a notification in a single call (POST /sheets/{id}/shares with sendEmail=true). The issue is determining who should receive access — the recipient may vary by project type, and building that logic adds more complexity than the time saved for a five-second manual click.

API reference: POST /sheets/{sheetId}/shares — the capability exists, but the recipient logic is the concern.
Cost Decision

Confirming the signed contract

Kept manual for cost

The API can confirm an attachment exists (GET /sheets/{id}/attachments), but it cannot read the document to verify a signature. Automating this would require either a strict file-naming convention or an AI step that opens and reads the attachment — both adding cost for a check that takes a person seconds to do visually.

API reference: GET /sheets/{sheetId}/attachments — can confirm a file is attached, but cannot verify its contents.

Error Handling & Reliability

The control script is designed to be resilient against transient failures, rate limits, and the asynchronous nature of the Smartsheet and Microsoft Graph APIs.

Rate Limits

Smartsheet allows 300 requests per minute per API token. Resource-intensive operations count 10x and are limited to 30 per minute.

  • 429 responses return errorCode 4003
  • The official SDKs implement exponential backoff automatically
  • For custom HTTP calls, implement exponential backoff with jitter and respect the Retry-After header
  • Batch row operations (up to 500 per call) to minimize request count
  • Execute updates to a single object serially to avoid save collisions

Async Operations

Sheet copy and OneDrive folder copy are asynchronous. The script must poll for completion before proceeding.

  • Smartsheet copy returns a Location header — poll until the operation completes
  • OneDrive copy returns a Location header — poll until the item appears in the target
  • Do not attempt to update or rename a resource until its copy is confirmed complete
  • Set a maximum poll duration (e.g., 5 minutes) and fail gracefully if exceeded

Filter Propagation Delay

Saved sheet filters take several seconds to propagate to Dynamic View and other dependent surfaces.

  • The Orders sheet filter must be created and saved before Dynamic View is opened
  • If Dynamic View was already open, reload the page
  • This is a human checkpoint concern, not a script concern — the script does not interact with Dynamic View

Script Idempotency & Recovery

If the script fails mid-run, it should be safe to re-run without creating duplicate artifacts.

  • Log the sheet copy ID immediately after creation — if the script restarts, it can check whether the sheet already exists
  • Use the Smartsheet-Change-Agent header on all writes to prevent duplicate updates
  • Each run should check for existing artifacts before creating new ones
  • Store run state (which phases completed) in a simple log or control sheet

Authentication & Security

The automation uses two separate authentication surfaces — Smartsheet and Microsoft Graph — plus a separate Dynamic View admin login for the manual step.

Smartsheet Authentication

  • Production: OAuth 2.0 app with scopes READ_SHEETS, WRITE_SHEETS, ADMIN_SHEETS, SHARE_SHEETS, CREATE_SIGHTS
  • Development: Personal access token (bearer) — simplest, but tied to a user and long-lived
  • Service account pattern: Use a dedicated Smartsheet user as the automation identity so shares and ownership are stable and not tied to an employee
  • Store all tokens in a secrets manager, never in code or .env committed to source control

Microsoft Graph Authentication

  • Requires an Entra (Azure AD) app registration
  • Least-privilege scope: Files.ReadWrite (not Files.ReadWrite.All unless needed)
  • Use delegated permissions if a user context is needed, or application permissions for unattended runs
  • Store the client ID, tenant ID, and client secret in a secrets manager

Dynamic View Credentials

  • Dynamic View has no API — OAuth scopes and service accounts do not apply
  • The separate admin login is stored in the "Smartsheet Admin" browser profile
  • If UI automation is ever used for Dynamic View, store admin credentials in a secrets manager and run the bot in a dedicated, isolated browser profile
  • Do not hardcode credentials

Security Considerations

  • Publishing a report or dashboard exposes data to anyone with the link unless access control is set to ORG or SHARED — set access deliberately
  • Sharing sheets programmatically may auto-convert users to paid members under the User Subscription Model — account for this in cost
  • The callback server must use a CA-signed TLS certificate and a public URL
  • Validate webhook callback signatures to prevent spoofed triggers
